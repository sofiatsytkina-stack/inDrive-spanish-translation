# Плейбук: локализация страницы-дубликата в Figma под рынок

Общая методология для превращения дубликата страницы ("English" → копия под конкретную страну) в
полноценную локализацию под рынок. Написан по опыту работы над Colombia в файле
[Delivery Product Flow Espanol](https://www.figma.com/design/2GDDIA8sTmlAARXtukZ6eB/Delivery-Product-Flow-Espanol),
но применим к Peru/Ecuador и к любому похожему кейсу (дубликат страницы под новый рынок).

## 0. Инструменты

Официальный Figma MCP-сервер: `get_metadata` (структура/дерево), `get_screenshot` (визуальная
проверка), `use_figma` (JS через Figma Plugin API — чтение и запись), `search_design_system`
(поиск компонентов библиотеки), `upload_assets` (загрузка картинок).

**Перед первым `use_figma` — обязательно подтянуть skill `figma-use`** (правила работы с API,
иначе типичные баги: незагруженный шрифт при правке текста, неправильное переключение страниц и т.д.)

**Проверить тарифный лимit заранее** (`whoami` + пробный лёгкий вызов) — на Starter-плане это
20 вызовов/месяц, легко упереться на середине работы. См. `README.md` этого хэндоффа за подробностями
одного такого затыка.

## 1. Разведка структуры (read-only)

- `get_metadata` без nodeId → список страниц файла.
- `get_metadata` на нужную страницу → дерево фреймов/секций. На больших страницах вывод может
  превышать лимит по размеру ответа — тогда сохранять в файл и парсить локально (grep/python), а не
  пытаться прочитать целиком через инструмент.
- Найти topmost-фреймы каждого логического "флоу"/группы экранов — это единица дальнейшей работы.

## 2. Ключевой трюк: дедупликация текста

Не пытаться перечислить и перевести каждую текстовую ноду по отдельности — в дизайн-системных
файлах с переиспользуемыми компонентами (варианты, состояния, инстансы) **реальное число уникальных
строк на порядок меньше числа нод**. Проверить сразу:

```js
const page = await figma.getNodeByIdAsync(PAGE_ID);
await figma.setCurrentPageAsync(page);
const nodes = page.findAllWithCriteria({ types: ['TEXT'] });
const set = new Set(nodes.map(n => n.characters));
return { totalNodes: nodes.length, uniqueCount: set.size };
```

Если uniqueCount << totalNodes (как здесь: 404 против 1379) — вся дальнейшая работа сводится к:
1. собрать список уникальных строк (чанками, см. ниже про размер ответа);
2. перевести/локализовать каждую один раз в таблицу;
3. одним скриптом-словарём пройтись по всем нодам страницы и заменить совпадения.

Если бы уникальных строк было почти столько же, сколько нод — тогда пришлось бы идти по группам
экранов с id, как в первоначальном (более медленном) плане.

## 3. Технические грабли этого конкретного MCP-сервера

- **Обрыв ответа на больших payload** (~20-28 КБ) — транспорт SSE ломается на `EOF while parsing
  a string`, это НЕ ошибка лимита. Лечится дроблением `return` на чанки по 40-60 объектов или ~50
  строк текста за раз.
- **Месячный лимит вызовов** (Starter-план) — это отдельная, более серьёзная проблема, не лечится
  ретраями или паузами. См. README.
- Каждый `use_figma` вызов сбрасывает `figma.currentPage` на первую страницу — обязательно
  `await figma.setCurrentPageAsync(page)` в начале каждого скрипта.
- Правка текста без предварительной `loadFontAsync` по текущему шрифту ноды падает с ошибкой.

## 4. Таблица локализации — расширяемый CSV

Один CSV на все рынки: `English, Colombia (ES), Peru (ES), Ecuador (ES), category, notes`.
`category`:
- `UI` — интерфейсный копирайт, обычно **одинаков для всех испаноязычных рынков** (не нужно
  переводить заново на каждый рынок — копировать из колонки Colombia, если не указано иное).
- `DATA` — пример данных (адрес/имя/цена/телефон/номер машины) — **разный на каждом рынке**.
- `SKIP` — служебная подпись дизайнера на канвасе (заголовок секции, имя фрейма) — не переводить
  никогда, ни для одного рынка.
- `CHECK` — что-то неоднозначное, нужен ручной взгляд перед применением.

## 4a. Регистр обращения: tú vs usted

Для всех испаноязычных потребительских рынков (Colombia, Peru, Ecuador и, вероятно, любых
последующих LatAm-рынков) используется **"tú"**, не "usted". Проверено на реальном копирайте
Uber Colombia и Rappi (прямые аналоги inDrive в этом сегменте: rides + delivery) — оба
последовательно на "tú", даже несмотря на то что разговорная Колумбия известна массовым бытовым
"ustedeo". Это устоявшийся индустриальный стандарт для потребительских приложений в испаноязычной
Латинской Америке, а не разовое решение под один рынок — не пересматривать заново для каждой новой
страны.

## 5. Что меняется от рынка к рынку (на основе референсов Colombia/Peru/Ecuador)

| Параметр | Colombia | Peru | Ecuador |
|---|---|---|---|
| Валюта/формат цены | `COP 13.500` (без `$`) | `S/ 16.50` (соли) | `$4.50` (USD) |
| Референс-город | Bogotá | (уточнить, вероятно Lima) | (уточнить, вероятно Quito/Guayaquil) |
| Формат адреса | `Calle 100 # 15-20` | Аналогичная система улиц/каррер, уточнить местные нормы | Уточнить местные нормы |
| Формат телефона | `+57 3XX XXX XXXX` | `+51 9XX XXX XXX` | `+593 9X XXX XXXX` |
| Флаг страны у поля телефона | 🇨🇴 | 🇵🇪 | 🇪🇨 |
| Модели транспорта (пример) | Chevrolet Onix, Bajaj Pulsar 200 | Toyota Yaris, Honda GL150 | Chevrolet Sail, Shineray XY150 |
| Гос. номера | `ABC123` (авто), `ABC12A` (мото) | Уточнить местный формат | Уточнить местный формат |
| Имена курьеров | Carlos/Juan/Mateo (короткие, муж.) | Оставить те же (по референсу — идентичны) | Оставить те же (по референсу — идентичны) |

**Важное наблюдение**: сравнение трёх скриншотов-референсов показало, что реальный продукт inDrive
использует **один и тот же UI-копирайт и одни и те же имена курьеров** на всех трёх рынках —
меняются только валюта и модель транспорта. Это сильно сокращает объём работы для Peru/Ecuador:
основной перевод (колонка `UI`) можно скопировать из Colombia, доперевести нужно только колонку
`DATA` (адреса/цены/телефоны/номера) под местные форматы.

## 6. Порядок записи правок

1. Собрать словарь `{English: TargetLang}` из CSV (только строки нужного рынка, без `SKIP`).
2. Один скрипт-цикл по всем `TEXT`-нодам страницы: если `characters` совпадает с ключом словаря —
   загрузить шрифт(ы) ноды → заменить `characters`. См. `figma-scripts/03-write-dictionary-replace.js`.
3. Отдельно — картинки (аватарки, флаг) через `upload_assets` + image fill override на инстансах,
   **никогда не на мастер-компонентах** (иначе затронет остальные страницы/рынки, использующие тот
   же компонент).
4. Верификация: скриншоты ключевых экранов + проверка, что другие страницы файла (English и уже
   готовые рынки) не изменились.

## 7. Порядок рынков

Colombia → Peru → Ecuador (по договорённости с пользователем). Каждый следующий рынок — быстрее
предыдущего, т.к. колонка `UI` в CSV уже переведена и переиспользуется.
